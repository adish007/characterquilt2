## 1. Establishing facts: measure, never reason

This is the core habit. **Do not reason about what the code does — run it.**

Almost every real finding last time came from executing something, not reading:

- Sweeping a parameter the demo held fixed (page size) revealed the same input
  producing three different answers.
- Running every fixture through every alternative implementation revealed all five
  broke the reader — two silently, three by hanging.
- Reconstructing a logged production run by replaying the code against a subset
  reproduced its exact numbers.

**When you state a number, show the command that produced it.** When you write a
plan, put measured "current" and expected "after" values on every item. It makes
the plan checkable and it catches your own errors — three of our plan's items were
wrong in ways only arithmetic exposed.

### Test your own conclusions, especially the satisfying ones

The most valuable thing we did was **attack our own strongest claim**. We had
argued a reconstruction was confirmed because three numbers matched. On inspection:

- one of the three was algebraically derived from another (`836 = 209 × 4`) — not
  independent evidence at all;
- another constrained the *count* of rows but said nothing about *which* rows;
- and a 15-line script showed the remaining match occurred in **47% of random
  perturbations**. It was the single most likely outcome by chance.

A claim you like is exactly the one to try to break. If you cannot think of a way
to falsify it, that is a bad sign, not a good one.

### Distinguish structural evidence from numeric coincidence

After that test, the reconstruction still stood — but on *structural* grounds
(clean ID-block boundaries, an independent document agreeing) rather than on the
arithmetic we had been citing. Same conclusion, completely different and much more
honest justification. Know which kind of evidence you actually have.

## 2. How to treat numbers in the starter

**Assume every number quoted anywhere is wrong until you derive it.** Last time the
README said 217, the event log claimed 209, the demo printed 214, and the file had
223 — four numbers, no two describing the same thing, none of them the answer.

- **Check units before comparing.** 217 was *rows*; 209 was *companies*. They were
  never comparable, and the apparent contradiction dissolved once that was named.
  Watch for this whenever two counts "disagree".
- **A number matching your expectation is not confirmation.** In our case the
  system reported the right total *for entirely the wrong reasons*: six spurious
  extras cancelled six missing items exactly. The shipped check agreed with it.
  This is why a count can never be the completeness test — only per-item
  reconciliation catches it.
- **Never hardcode a fixture count**, in code or tests. Compute it (`len(rows)`),
  or assert an invariant instead.

## 3. How to decide things

### Cause versus symptom, stated honestly

The brief warns: *"Removing a symptom is not the same as removing its cause; both
can be right under time pressure, but shipping one while describing it as the
other is not."* Keep an explicit table. Ours had a row that read, in effect, "we
detect this; we cannot prevent it, because the cause is upstream of this repo."
That honesty is worth more than an inflated claim.

### Asymmetric failure modes decide close calls

When two options are both defensible, ask **which way of being wrong is
recoverable**. Ours: merging two records that should stay separate silently
deletes one — invisible, and the exact defect we were fixing. Not merging when we
should have produces a visible duplicate — obvious and cheap to undo. That
asymmetry, not confidence about the truth, settled it.

### Report, but admit you decided

We initially wrote "we report them, we don't decide." That was wrong and the human
caught it: shipping output *requires* deciding. The honest formulation is:

> We decided. We chose the direction that fails recoverably, we changed nothing
> irreversible, and we made the decision visible so it can be overruled.

"I didn't decide" is a dodge a reviewer will poke at. Never claim it.

### Don't repair what you can't tie to the complaint

There will be **planted noise** — plausible-looking failures with no connection to
the stated problem. Ours was a retryable timeout plus a self-healing cache warning.
Identifying them as noise and *saying so* in the write-up is worth more than
fixing them. Second task warns some of the eleven labelled cases are exactly this.

## 4. How to test

Green tests prove nothing on their own. The brief says so: *"`make demo`, `make
test` and `make verify` already run clean on the starter, so a green run is not
evidence that you are done — and neither is a green run of checks you wrote
yourself."*

What actually earns confidence:

- **Adversarial tests.** Build a *correct* artifact, damage it one way at a time,
  and require rejection each time. We ran eight — dropped item, doubled output,
  orphan record, wrong attribution, unauthorised config, emptied disclosure block,
  and a plan that *asserted its own success while missing data*. That last one is
  the important one: it proves the check isn't reading the subject's own claim.
- **Mutation testing.** Copy the source to a scratch dir, revert each fix in turn,
  confirm a test fails. Seven of seven caught means something; "26 tests pass"
  alone means very little.
  - **Watch for ineffective mutations.** One of mine "survived" — but only because
    my replace string didn't match the real line, so nothing was mutated. Always
    assert the mutation actually applied before trusting a survivor.
- **Tests that assert a limit.** Where something is genuinely undetectable, write
  a test asserting the indistinguishability. Then the limit is recorded rather
  than assumed, and it can't silently regress into a false claim.
- **A guard that stays silent is fine — say so.** We shipped a check that reports
  zero on both fixtures. That is the point: *a guard that never fires on the data
  it was written against cannot have been fitted to it.* Log it as deliberately
  empty so silence isn't read as an omission.
- **No fixture-specific values in assertions.** No literal IDs, names, or counts.
  Build small synthetic inputs for specific behaviours; parameterise over both
  fixtures for invariants.

### Know what your held-out set cannot test

A second fixture is there to distinguish a fix from a fit — but be precise about
its blind spots. Ours could not test the central identity policy (it returned the
same answer under either rule) and could not exercise one whole failure mode. Say
this out loud in the write-up. It reads as rigour, not weakness.

## What the system actually does

The relay stores deployments in SQLite, writes drafts to a JSON-backed fake HubSpot, then stores a receipt. Its durable recovery mechanism is sound only for a single interrupted run: provider keys are stable within that run, so replaying a write does not duplicate it.

Everything labeled “verified” is local assertion rather than verification:

- `run_once()` sets `"verified": True` unconditionally.
- `audit()` rereads the stored receipt, not HubSpot.
- `deployment_summary()` also reports only the receipt.
- `make stress` prints a computed “objects created” value and never rechecks provider state after recovery.

Relevant code: [relay/core.py](/Users/jaina/Downloads/02-durable-run-relay/relay/core.py:115), [stress.py](/Users/jaina/Downloads/02-durable-run-relay/stress.py:54), [tests/test_visible.py](/Users/jaina/Downloads/02-durable-run-relay/tests/test_visible.py:41).

## Root causes

The central causes are:

- No uniqueness or conflict semantics for idempotency keys.
- Provider keys include the newly generated run ID, making admin retry a new deployment.
- No exclusive or leased worker claim.
- Concurrent read-modify-write access to the provider state is uncoordinated.
- Cancellation is not part of execution’s state machine.
- Receipt verification is unconditional.
- Audit never contacts the provider.
- Recovery does not isolate failures.

The provider’s 40-character normalization is not itself ours to change. We can prevent incompatible requests before writing and verify returned data. Merely changing `verified` to false afterward would detect the symptom while leaving incorrect drafts behind.

## Promise I recommend

A defensible narrow contract would be:

1. Repeating the same key and payload returns the same logical deployment; reusing the key for different content is rejected.
2. A run succeeds only after every approved asset has exactly one provider draft whose identity, hash, type, status, and required display fields match.
3. “Check again” performs fresh provider reads.
4. Crashes and ambiguous write outcomes may repeat calls but do not repeat effects.
5. Concurrent workers cannot process the same run or corrupt shared provider state.
6. Cancellation prevents new writes after cancellation is observed; it does not delete drafts already created.
7. One unrecoverable run is reported independently and cannot stop later runs.

It still cannot promise atomic all-or-nothing deployment, rollback of accepted provider writes, permanent provider retention, or exactly-once network calls.

## 3. Cancellation behavior

Cancellation is only an unconditional SQL update:

- A cancelled run can be executed normally.
- Cancellation after the first write does not stop the remaining three writes.

- A partial run cancelled after a crash remains one provider object with no receipt; recovery ignores it.
- A cancelled or completed run can be manually executed again.
