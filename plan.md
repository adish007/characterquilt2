# Plan

Implement the operator contract with the smallest durable design that works across multiple worker processes: SQLite owns request identity and fenced run claims, while a relay-side inter-process gate serializes access to the provider's unsafe whole-file operations. Each numbered item is one review and commit boundary; tests and implementation land together so every boundary keeps `make demo`, `make test`, and `make stress` runnable. The human operator will make commits after reviewing each boundary.

## Scope

- In: request validation and idempotency, same-run retry, operator-visible outcomes, durable claims and fencing, cross-process provider coordination, exact reconciliation, cancellation, live audit, recovery isolation, truthful demo/stress output, and contract-focused proof.
- Out: changing `FakeHubSpot`, deleting historical duplicate/partial drafts, real HubSpot/network work, all-or-nothing rollback, UI/framework work, SQLite WAL tuning, and final event-case interpretation already handled separately.

## Action items

- [ ] **1. Enforce valid immutable requests and stable logical identity (`relay/core.py`, `relay/__init__.py`, request tests, `demo.py`, `stress.py`).** Fix the current behavior where every submit creates a UUID, the same key accepts different payloads, malformed assets fail only during execution, duplicate asset IDs collapse, and known display-name normalization is discovered after writes. Validate before reserving the key: supported destination/mode, explicit list-valued `assets`, non-empty string `asset_id`/`source_sha256`/`type`/`display_name`, unique asset IDs, and names already equal to the fake provider's known strip/40-character representation. Keep explicit `assets: []` as a valid verified no-op. Add a unique SQLite index on `idempotency_key`; perform lookup/insert in one `BEGIN IMMEDIATE` transaction so concurrent submissions cannot race. Same key plus same canonical hash returns the existing run; same key plus another hash raises `IdempotencyConflict`; rejection creates no row and does not reserve the key. Return a small `SubmissionResult` containing `run_id`, whether it replayed an existing request, and prior different-key run IDs with the same `payload_hash`. Keep provider effect keys scoped to the stable run ID. Make `retry()` requeue/return that run rather than inserting a new row. Add an additive schema migration and fail startup clearly if historical duplicate keys prevent the unique index; do not merge or delete them. Update existing callers and use the short-name fixture for successful deployment paths while the main fixture explicitly demonstrates zero-write rejection. Prove validation produces zero provider calls, corrected content can reuse a rejected key, identical payload under a different key is disclosed but allowed, repeated retry never exceeds the payload-derived object count, and concurrent same-key submits produce one row.

- [ ] **2. Introduce explicit outcomes and durable fenced claims (`relay/core.py`, state/recovery tests).** Fix unguarded transitions that let any caller drive `pending`, `running`, `done`, or `cancelled` and let stale workers overwrite newer results. Add `error_json`, `claim_token`, and `claim_expires_at` through the schema migration and support `pending`, `running`, `retryable`, `cancelling`, `cancelled`, `failed`, and `done`. Inject a clock and configurable claim TTL for deterministic tests. Atomically claim only pending/retryable work or running work with an expired claim; renew synchronously before each new provider operation. Every status, error, and receipt commit uses the claim token as a fencing predicate and checks the affected row count. A call started under a valid claim may finish after expiry, but the stale worker cannot start another call or commit afterward. `retry()` keeps the same run/effect namespace and only requeues an eligible retryable or expired run; terminal conflicts require operator attention. Make each recovery pass consider pending and expired/interrupted work, skip active claims, and catch/record errors per run so a poison row cannot stop later candidates. Also finalize interrupted `cancelling` work. Prove one active claim, pending pickup, active-claim non-theft, expired-claim recovery, renewal, stale-worker fencing, same-run retry, poison-run isolation, and visible non-success for unresolved work.

- [ ] **3. Serialize every relay-owned provider operation across processes without changing the provider (`relay/core.py`, process-concurrency tests).** Fix lost updates, transient/trailing-byte `JSONDecodeError`, and read-after-write `KeyError` caused by concurrent whole-file load/mutate/save. Add one small provider coordinator using a POSIX advisory lock file derived from `provider_state_path`; the OS releases it if a worker dies. Route create/read pairs, reconciliation/listing, audit, and cancellation reconciliation through this gate with one consistent lock order. Do not add a process-local mutex, modify `FakeHubSpot`, introduce WAL, or claim atomic external transactions. Hold the gate for the smallest complete provider operation; different runs may still execute concurrently outside it. Recheck claim/status after taking the gate and before starting a call. Add deterministic multiprocess tests for distinct runs and same-run contention, asserting payload-derived provider keys/counts, readable JSON, no lost updates, and no worker error hidden by a sibling receipt. Include a control that proves an already-started call may finish after claim expiry while its stale worker remains fenced. This removes relay-caused concurrency corruption; provider drift or a crash inside provider persistence remains visible through reconciliation rather than being called success.

- [ ] **4. Replace asserted verification with exact reconciliation and truthful failure records (`relay/core.py`, reconciliation/audit tests).** Fix literal `verified: true`, count-only receipts, partial effects hidden during interruption, and receipt-only audit. Centralize one reconciliation function that derives expected external keys from the stored payload, reads the current provider namespace through the coordinator, and reports missing, unexpected, duplicate, or field-mismatched objects. Require exact asset ID, SHA, type, display name, and `draft` status. Record the actual objects and issues in receipts for success and partial terminal outcomes. A successful pass means each object matched when individually read immediately before the fenced `done` commit; do not imply an atomic snapshot. Classify missing objects, temporary unreadability, timeouts, and unresolved acceptance as `retryable`/unknown; classify an existing effect identity with conflicting content or deterministic field mismatch as terminal `failed`. On an accepted-write timeout, read back the same effect identity before deciding whether replay is needed; replay never changes identity. Make `audit()` perform fresh reconciliation and return detailed false results instead of raising or trusting the receipt. Keep `deployment_summary()` explicit about stored terminal outcome versus current audit state. Prove exact success for short and empty fixtures, preflight rejection for the main fixture, accepted-write readback, provider-conflict failure, partial-effect reporting, and live detection of deletion, mutation, duplication, unexpected objects, and unreadable state.

- [ ] **5. Make cancellation a coordinated state transition with complete partial reporting (`relay/core.py`, cancellation tests).** Fix cancellation being overwritten by `running`/`done`, execution continuing through all assets, and accepted effects being hidden. First durably set `cancelling`; workers must check status after acquiring the provider gate, so no new call starts after acknowledged cancellation intent. The cancel path then takes the same gate, waits for any already-started call to return, performs current reconciliation, and writes `cancelled` with an unverified partial receipt using a guarded transition. If the provider cannot resolve an in-flight outcome, retain visible `cancelling`/unknown state for recovery rather than fabricate certainty. Old workers cannot commit because their status/token predicates fail. Do not delete accepted drafts. Use deterministic barriers to prove cancellation before work writes zero, cancellation between assets prevents the next call, a call already in flight may finish and appears in the report, cancellation cannot relabel `done`, and stale workers cannot overwrite the terminal state.

- [ ] **6. Make the required demonstrations measure the contract (`demo.py`, `stress.py`, `Makefile`).** Replace reassuring arithmetic with observed and reconciled state. `make demo` should first show the main request rejected with zero provider effects, then use the short fixture to show expired-claim crash recovery without duplicate effects, and finally damage provider state so live audit reports exact missing objects. `make stress` should exercise actual worker processes, use the valid short fixture, report expected versus current provider keys, SQL status/receipt/error counts before and after recovery, and fail if provider state is unreadable, any worker error is hidden, any run remains nonterminal unexpectedly, or reconciliation differs. It must also show that independent per-run failures do not halt the rest of the pool. Keep counts derived from payloads and worker lists, never fixture literals. Run each command repeatedly enough to establish determinism, but report sample sizes rather than presenting scheduling frequencies as probabilities.

- [ ] **7. Prove each guarantee and its limit before final documentation (`tests/`, temporary mutation harness, `DECISIONS.md`, `SUBMISSION.md`).** Organize synthetic contract tests by request identity, claims/recovery, provider coordination, reconciliation/audit, cancellation, and failure reporting; parameterize applicable invariants over short and empty fixtures. Add adversarial cases for dropped, changed, duplicated, unexpected, unreadable, and ambiguous provider outcomes and a subject that falsely asserts its own success. Mutation-test every load-bearing repair in a scratch copy, first asserting each mutation applied: remove key uniqueness, skip validation, remove claim-token predicates, bypass the provider gate, restore unconditional verification, make audit receipt-only, ignore cancellation, and restore fail-fast recovery; each must cause a named check to fail. Record negative results too: no claim of atomic provider snapshot, rollback, exactly-one call, provider permanence, or cleanup of historical drafts. Run `make demo`, `make test`, and repeated `make stress` after every reviewed boundary and once more together. Only after the evidence is green should the final operator wording, cause-versus-symptom table, remaining unsafe behavior, time spent, and command outputs be written.
